Frontend audit · 5 September 2026

What design-os specified,
and what the app actually ships

The design-os/ folder names 30 routes across Phase 3's sitemap and blueprints 27 of them in Phase 4, composed from Phase 5's 70 reusable sections. Every one of those routes was checked against the App Router tree and the section components that render it. The headline: the portals overshoot the spec considerably, and the gaps concentrate in three places — anything geographic, anything that moves a file, and the depth of the offer workflow.

Ship-blocking first Two defects, not spec drift

These are not disagreements with the blueprint. They are links the app renders today that resolve to the 404 page.

Seven routes are linked from the site chrome but do not exist

The footer renders three link columns and the public header renders a primary nav; between them they point at seven paths with no page.tsx. /about and /contact sit in the primary navigation on every public page. /privacy and /terms are additionally referenced from AUTH_ROUTES in lib/constants.ts, so the signup consent copy links to them too. design-os names About, Help, Blog, Privacy and Terms as footer content in Section 48 but never blueprints them as pages — so the spec is complicit here, and the fix is a decision about scope, not just a missing file.

/about /blog /contact /help /privacy /terms /accessibility components/layout/footer.tsx lib/config/site-nav.ts

The Quick Actions panel is written, exported, and imported nowhere

components/features/shared/quick-actions.tsx is dead code — no file imports it. It is also precisely the module design-os asks for three times: Page 8 module 5 (buyer dashboard "Quick Links"), Page 15 (agent dashboard "Quick links") and Page 20 module 7 (admin overview "Manage Users · Review Listings · Process Verifications · View Reports"). All three pages currently render without it. One component, three unfilled slots.

Reading the ledger

01

The spec is now the smaller document. design-os blueprints 27 pages from 70 sections; the app ships 36 page routes composed from 206 section components, 269 feature components, 47 primitives and 33 patterns. In the admin console especially, the built screens exceed their blueprints in almost every module. Treating design-os as the authority would mean deleting good work — the honest read is that it has fallen behind the code and needs a Phase 4 revision, not that the code has drifted.

02

One unmade decision explains three gaps. /map, the search Map toggle and the listing Neighborhood section are all blocked on the same thing: no map provider has been chosen or installed. Picking one closes a whole column of this ledger; leaving it open keeps the public surface permanently short of its blueprint.

03

Nothing in the app moves a file between two people. No message attachment, no document share, no drag-drop upload, no document step on an accepted offer. For a marketplace whose spec has buyers and agents exchanging inspection reports and appraisals, this is a coherent functional hole rather than four unrelated misses.

04

Two screens read but cannot write. The agent pipeline shows stages without letting an agent change one; the agent calendar shows a schedule without letting an agent add to it. Both are presentation-complete and interaction-incomplete, which is the failure mode most likely to be mistaken for "done".

05

Divergences worth ratifying, not fixing. The saved-listings table over a card grid, price chips over a slider, token-link password reset over OTP, and the Concierge narrative over a four-step "How It Works" all look like considered decisions. They are only problems because the spec still says otherwise. Amending Phase 4 and 5 to record them would shrink this ledger by four rows without touching a line of code.

Remediation · 8 September 2026

The findings above stand as recorded on 5 September. This section reports what changed three days later, when the “built, modules short” bucket was worked through. Nothing above has been edited.

10Routes closed
3Still short
4Sections closed
2Ratified, not built

Closed

/dashboard gained modules 4 and 5 — New Alerts, banded from PRICE_DROP and NEW_LISTING notifications, and Quick Links. /agent and /admin gained their quick-link panels; the orphaned quick-actions.tsx was replaced by a shared quick-action-list consumed by all three, so the dead-code defect above is closed with one component rather than three.

/admin/settings gained the Reporting Timezone field, the remaining six policy toggles across the spec’s two groups — Moderation Policy and Operations, eight in total — and the Section 70 Maintenance Panel, whose two actions are backed by new endpoints rather than stubs. The Reach column, whose header had no cell and whose PolicyReachMeter was a second orphan, now renders.

/agent/calendar can write: Create event proposes viewing times against an existing connection through the endpoint that already existed. /agent/pipeline is no longer read-only — cards drag, and a per-deal detail modal opens. /agent/leads gained the missing scoring dimension. /signup gained the password strength meter and the Facebook mark.

Files now move between people. Section 38 shipped as a real FileUpload primitive with a drop zone, keyboard operation, stated type and size limits and a progress bar fed by actual upload progress; both former <input type="file"> controls were retrofitted onto it. Section 23 put an attach control on the composer, and Section 25 shipped as document cards in the thread, a Shared Documents panel in the context rail, and attachments on offer detail. A MessageAttachment model and a POST /messages/:id/attachments route carry it, over the Cloudinary document upload that was already built and unreachable.

The map column, closed

Note 02 above needs one correction: a provider was never the only blocker. Property.latitude and longitude were nullable, never seeded and never mapped onto Listing, so picking a provider first would have rendered an empty basemap. Coordinates came first — a locality centre table with deterministic per-property placement, a scoped backfill, Listing widened, and a bounding-box filter on property search — and only then the library.

MapLibre GL with keyless OpenFreeMap tiles now renders /map (Page 4, with the filter rail, pin peek card and legend), the Map option on the search view toggle, a placed map on listing detail, and a sales map on the home page beside the existing card row. ADR 0015 records the ordering and the provider choice.

Still short

Section 10’s school, transit, park and restaurant markers and their toggleable legend are the one piece of the map work still owed. They need a POI dataset the platform does not have, and placing invented school pins on a listing would be the same fabrication the coordinate work was careful to avoid.

Signup OTP, /verify-email, working OAuth for any provider, and Google Calendar sync remain outstanding and are listed with their blockers in design-os/INDEX/RATIFIED_DIVERGENCES.md.

Ratified rather than built

Note 05 proposed amending Phase 4 and 5 to record the considered divergences. That was done the other way round: the phase documents were left untouched, and design-os/INDEX/RATIFIED_DIVERGENCES.md now reconciles spec against code in one place. The lead status taxonomy joined that list — pending/accepted/declined stays, because the spec’s four states cannot be populated from any existing signal and the enum is load-bearing in common/access.ts. The hot/warm/cold dimension the same row asked for was added instead, derived on read from offers, viewings, unread messages and contact recency. ADR 0016 records it.
